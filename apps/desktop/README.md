# Windows desktop preview (experimental)

The repository now contains an Electron desktop shell for an **experimental local OBS HUD preview and local CS2 observer input**. It bundles Chromium and Node with the application, opens the same local HUD used by the browser demo, provides a separate sandboxed operator-controls window, and owns/stops the GSI ingest + timeline + overlay services. The embedded renderer cannot access Node APIs or the randomly generated ingest secret. Live and Demo modes are separately started and shut down inside the desktop main process. The HUD continues to show **DEMO · SYNTHETIC DATA** and the uncalibrated radar warning.

## Local development

Install dependencies with `npm install` (Node.js 22+ required *for development*), then run `npm run desktop`. The preview window opens, and **Broadcast → Copy OBS Browser Source URL** copies the loopback address for OBS. Closing the window stops its owned HTTP services.

Ports 3008 and 3009 must be free. If a separate `npm run demo` session is still running, terminate it first. The desktop application does not terminate other programs or take over their ports.

## Guided local setup in Operator Controls

Open **Broadcast → Operator Controls** to use the three-step setup panel. Select Demo or Live without hunting for menu entries, explicitly export the observer CFG through the native file dialog (Live only), and copy the local OBS Browser Source URL. The panel includes the last authenticated GSI freshness state from the same trusted IPC as before. It never accesses the GSI key, writes the CFG silently, or changes the DatHost server. Native dialogs are still shown for exports and mode confirmation; a cancellation is not treated as a successful export.

Status refreshes are request-ordered: when periodic polling overlaps a Demo/Live switch or a slower prior poll, only the newest requested response may update the operator display. An outdated error cannot replace a newer successful connection state. This guards against misleading status and incorrectly enabled controls but does not establish live observer correctness.

The guided control script now also has deterministic interaction tests running its actual event handlers against a simulated DOM and IPC boundary. They exercise mode switching, export/copy, cancellation/error feedback, disabled states and team settings. These tests do not click native Windows dialogs or validate a real CS2/GOTV feed.

This is **not** a full Windows installation wizard: real CS2/GOTV and OBS acceptance still require an operator test.

## Built-in operator controls

Open **Broadcast → Operator Controls** (or `Ctrl+,`) inside the desktop preview to edit CT/T team names, accent colors and roster visibility. Changes apply to the OBS preview without restarting the app and are stored as validated public-only settings at `<Electron userData>/operator-settings.json`. This file contains no credentials. The controls use restricted Electron IPC rather than a browser-accessible administrator port: no administrator token is exposed to the renderer, and there is no open port 3010 for the desktop version. No remote operation or team-side data access is provided.

The demo preview and operator panel are separate windows. Close the main HUD window to stop the owned receiver and HUD servers. Settings persist across desktop restarts, but are scoped to this Windows user and this app build.

## Switching between Demo and local CS2 Live Observer

If the demo's local synthetic GSI writer temporarily fails or hangs, the application bounds each request to 1.5 seconds, removes old map, round, both team scores, phases, countdown and roster from the public HUD JSON after retries fail (not merely changing its status), displays **DEMO · DATA INTERRUPTED** in Operator Controls and retries automatically at the normal demo interval. An in-flight synthetic request is cancelled on shutdown, so the desktop can release its loopback listeners without waiting for an unresponsive fetch. At most one synthetic update runs at a time. After a successful update, the animated demo returns. Persistent failures still require checking the app or local machine; no real CS2 traffic is involved. This is not a guarantee of recovery from a terminated process or a receiver socket failure that cannot be repaired in-process.\n\nThe app starts in **Demo** mode. Use **Broadcast → Start Live Observer** to stop the synthetic feed and begin waiting for a real, authenticated **local** spectator GSI source. While waiting, the HUD intentionally shows unavailable rather than fake scores. Live output explicitly identifies itself as non-demo even before any authenticated GSI arrives, so switching Demo → Live removes the synthetic watermark immediately; a temporary OBS HTTP failure cannot override the last explicitly known source mode. Open **Broadcast → Operator Controls** for actionable diagnostics: **Waiting** means no authenticated GSI update has ever arrived; **Receiving** means authenticated updates arrived recently; **Interrupted** means a previously connected source has gone stale. The window displays seconds since the last accepted update, plus a state-specific setup/recovery hint. The status also distinguishes receiving authenticated GSI from having enough reported fields for a basic map/round/two-score HUD. An incomplete HUD may coexist with a connected source; the operator window uses an amber warning accent for connected-but-incomplete coverage instead of the normal connected green accent. Connection and coverage remain separate signals, and the coverage indicator is **not** independent validation of accuracy. These indicators cannot diagnose Valve/GOTV sync or prove an actual match is correct. Use **Broadcast → Start Demo** to switch back.

In Live mode choose **Broadcast → Export CS2 GSI Config…**. Save `gamestate_integration_anocore.cfg` into your CS2 installation's `game/csgo/cfg/` folder (for example under the Steam Counter-Strike Global Offensive installation). The app searches the standard Steam directory and libraries registered in `libraryfolders.vdf`, then offers a detected CS2 game configuration folder for confirmation. A manual Save dialog remains available if Steam is installed elsewhere, the library metadata is invalid, or CS2 cannot be located. The discovery process only reads local Steam metadata; it does not change Steam or your game files unless you explicitly save. You may save elsewhere and copy it yourself. Restart the game, run a **spectator/GOTV observation** that supplies the requested data, and keep Live mode running.

The exported CFG contains a randomly generated authentication key required by CS2. **Treat the CFG as a secret and do not share it.** On Windows, Electron's OS-backed safeStorage encrypts the key for the current Windows user and saves only the ciphertext at `<Electron userData>/observer-credential.json`. The same key is reused after normal application restarts and Demo/Live switches, so **you do not need to re-export the CFG after each restart**. No key appears in the operator settings file, browser state or renderer. Encryption/decryption failures and corrupted credential files block Live mode instead of silently changing the key. To rotate the key, first switch to Demo, select **Broadcast → Reset saved GSI key…** and explicitly confirm. Then start Live, export a new CFG and deliberately replace the old game file. The app refuses to overwrite an existing CFG automatically, even if the Save dialog confirms replacement. Resetting a saved key does not edit any existing game file. A different Windows account may not be able to decrypt this user's key. Do not delete a damaged key file or reset it without understanding that you will have to replace the CS2 CFG. Do not share exported CFGs because they contain the session credential. This initial version assumes CS2 and the application run on the same Windows machine and listens on `127.0.0.1:3008`.

Desktop Live uses a **volatile, 10,000-event rolling observer window** with no replay delay or persistent journal. Unlike the strict engine used for verified replays, this preview can keep accepting consecutive authenticated GSI frames during long sessions without locking up at the first 10,000 updates. Old events are evicted and cannot be replayed or recovered; this is not a recording feature or verified GOTV synchronization. Closing the desktop app discards this in-memory timeline.\n\nThe local CS2 GSI HTTP receiver rejects incomplete bodies after a 5-second deadline without committing a match update. Switching modes or quitting closes its own pending loopback sockets immediately, avoiding a hung partial request that blocks shutdown. This does not affect other apps' ports or establish actual GOTV synchronization.\n\nIn that rolling Live window, consecutive authenticated packets are selected by source sequence rather than by a potentially backwards-adjusted Windows wall-clock timestamp, preventing an older score from winning after a clock correction; freshness and future-frame gating still apply.

The OBS Browser Source URL remains `http://127.0.0.1:3009/`, copied via the Broadcast menu. The OBS HUD requests state every 500 ms, applies a 2-second per-request deadline (including JSON parsing), limits concurrency to four polls and blanks previously displayed scores, roster, timer and radar after more than 3 seconds without a successful latest update, even if HTTP requests remain stuck. Once a valid state arrives again, it resumes rendering. Temporary HTTP failures preserve only the last explicitly known Demo/Live watermark mode, **not** old scores. This fail-closed browser-side protection complements source freshness checks but cannot establish CS2/GOTV video synchronization. The live HUD does **not** include the synthetic demo radar, does not publish player world coordinates, and has no verified GOTV/video-frame synchronization. Test the source using an authorized observer only; this integration has not yet undergone a real CS2 or clean Windows acceptance test.

## Download a tested Windows EXE from merged main

After a relevant merge into `main`, the **Windows desktop preview** workflow runs again against the **merged commit** (not merely the earlier PR head). Open the [Windows desktop preview workflow](https://github.com/nfloser/anocore-broadcast/actions/workflows/windows-desktop.yml), choose the most recent **successful main-branch run** and check its commit SHA against the commit intended for the CS2/GOTV acceptance session. On the run page, download the `anocore-broadcast-windows-preview` artifact from **Artifacts** and extract the EXE alongside `SHA256SUMS.txt`. This is an unsigned preview artifact retained for 7 days, not a production release.

From PowerShell in the extracted artifact directory, verify its actual filename against the checksum file:

```powershell
Get-Content .\SHA256SUMS.txt
Get-FileHash '.\AnoCore-Broadcast-0.1.0-win-x64.exe' -Algorithm SHA256
```

Compare the hex hashes (case-insensitive), then note the run URL and merged SHA in the [real observer acceptance record](./REAL-OBSERVER-ACCEPTANCE.md). If the artifact has expired, explicitly re-run the workflow on `main` using **Run workflow**; do not substitute an unverified local build. Never treat a successful packaged start/stop check as real CS2/GOTV acceptance.

## Privacy-safe live diagnostic sharing

When reproducing an issue with a real CS2 spectator, open **Broadcast → Operator Controls** in **Live** mode and choose **Copy safe diagnostics**. The application creates a small, allowlisted JSON report of observer freshness, HUD field availability and player count directly in the main process, then copies it to the clipboard on request. The controls renderer gets only a success/failure response. The report now also includes counts across the last **64 accepted authenticated GSI updates** for fixed field-shape categories: map, round, a complete *same-message* map name/round/both-side-score combination, allplayers, explicitly empty or nonempty allplayers, phase_countdowns, previously and added. Zero scores count as present; malformed or missing core fields do not count as complete. A complete-field count is **not** a claim that the scores are correct or synchronized. It also calculates aggregate transitions within the current 64-message window (complete scoreboard becoming incomplete or complete; a nonempty roster disappearing or reappearing) and the longest incomplete-scoreboard streak in number of accepted messages. The first message in the window has no predecessor, and evicted messages never count toward transitions. This helps distinguish sporadic omissions from long incomplete runs without reconstructing or exporting chronological frames. It reports only bounded aggregate numbers, not individual update order, source timestamps, values or raw frames. Rejected requests are excluded; counts reset when a Live service starts and do not persist to disk. Compare several such privacy-safe summaries while actually spectating to establish whether omitted versus empty fields occur; the counts alone cannot establish the meaning of omissions. This report intentionally omits player/team names, map names, Steam IDs, positions, weapons, raw event details and GSI authentication keys. It is useful for spotting missing categories of data, not for diagnosing exact Valve GSI field semantics or video-frame synchronization.

The copy action is available only in Live mode. Never share the exported `gamestate_integration_anocore.cfg`, a raw GSI packet, the encrypted observer key file or screenshots containing private details. Safe reports do not replace authorized real-world observer acceptance.

## Independent GSI contract validation

In addition to the synthetic animated demo and Windows packaged-runtime check, CI now submits a **separately authored CS2-shaped observer GSI sample** to the real authenticated desktop Live receiver. Assertions check provider compatibility, map/score/round projection, ten-player details, active weapons, utility, strict removal of Steam IDs/positions/tokens and synthetic radar, unauthorized rejection, recovery after stale data, and deliberately partial GSI fields without guessed values. This sample is **synthetic, not a capture from a real CS2 match**; CI proves the documented processing contract, not source compatibility or video-frame synchronization on a particular observer build.

For a repeatable, privacy-safe operator procedure with A01–A13 acceptance cases, D0–D4 diagnostic checkpoints, evidence templates, and explicit release gates, use [Real CS2/GOTV + OBS acceptance protocol](./REAL-OBSERVER-ACCEPTANCE.md). This document is a **plan**, not a claim that acceptance was performed.

For real-world acceptance, keep the desktop in Live mode with the saved CFG installed and monitor the **Receiving GSI** status while spectating. Compare map, score, round, health, equipment, player identities and phase timers directly against the observed CS2 spectator view and the OBS browser source. Document any inconsistencies with exact CS2 version, mode, observed field/phase and result, but **never attach the GSI CFG or any file containing the authentication key**. A real CS2 + OBS end-to-end acceptance remains a release blocker.


### Sequential partial-frame regression contract

The synthetic HTTP integration tests also send **successive** observer messages (complete 5v5 state, provider-only partial state, explicitly empty `allplayers`, then another complete state). In the current implementation each accepted message is a standalone snapshot: omitted scores and players do **not** carry forward, an empty roster stays empty, and a subsequent complete message restores available values. A fresh GSI connection can therefore coexist with an incomplete HUD. This is intentionally characterized by tests, **not** proof that real CS2 spectator GSI omissions mean removed rather than unchanged. Do not add speculative merge behavior or assume production readiness until the permissioned real-observer verification in Issue #62 resolves actual payload semantics. Stale expiry continues to hide the whole public snapshot.

## Windows packaged runtime smoke test

The Windows CI workflow now launches the **packaged unpacked Electron executable** from `dist/win-unpacked` (the same packaged application image used for the portable EXE), waits for the loopback OBS HTML and sanitized synthetic 5v5 JSON to become available, requests normal main-window shutdown, verifies that both local ports are released, and repeats startup/shutdown to catch restart regressions. The smoke-test executable includes its own Electron runtime; it does not rely on a system Node installation at runtime. On failure, the CI job fails before publishing a preview artifact.

This is a **Windows CI-runner check only**, not a hands-on clean-PC Windows or Defender test and not proof that real CS2/GOTV observer data is correctly presented.
